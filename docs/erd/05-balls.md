# 5. balls — 구슬

> 기획 근거: [기획정리.md](../기획정리.md) 3 · 4 (구슬이 생기는 때), 5. 구슬 넣기 연출, 6. 유리병 선반
> 앞 단계: [answers](04-answers.md) / 다음 단계: ghosts(6번)
> 미정 사항: [A-10 퇴사각 지수 계산 방식](../기획정리_추가정리필요요소.md) · [A-9 점수 변환](../기획정리_추가정리필요요소.md)

## 왜 필요한가
- **유리병 선반에 진열되는 구슬**을 저장하는 곳. 구슬을 누르면 보이는 **퇴사각 지수(숫자)** 도 여기 있음
- 구슬은 두 종류
  - **오늘의 구슬**: 하루 **1개**. 오늘의 질문에 **첫 답**을 하면 자동으로 생기고, 2 · 3번째 답은 **같은 구슬에 담김**
  - **특별한 구슬**: 이달의 질문에 답하면 오늘의 구슬과 **따로 1개가 더** 생김. 반짝이는 **모양**으로 구분
- 답을 하나도 안 한 날은 **구슬이 없음** (줄이 없음)
- `kind` 는 [questions.kind](02-questions.md) 와 **같은 값(`short` / `long`)**: 단기 질문의 답은 `short` 구슬에, 장기 질문의 답은 `long` 구슬에 담김. 한 구슬에 단기 답과 장기 답이 섞이지 않음

## 예시 데이터

사용자 `a1b2…` 의 구슬 (점수는 [answers](04-answers.md) 예시와 이어지는 **임시 값**)

| id | user_id | kind | ball_date | score (퇴사각 지수) |
| --- | --- | --- | --- | --- |
| `b1…` | `a1b2…` | short | 2026-11-20 | 62 |
| `b2…` | `a1b2…` | short | 2026-11-21 | 55 |
| `b3…` | `a1b2…` | long | 2026-11-05 | 25 |

- `b2…` (11-21): 그날 답 2개(점수 70, 40) → 임시 규칙으로 **평균 55**
- `b3…` (11-05): 이달의 질문 복지에 답한 특별한 구슬. 답 1개의 점수 **25**
- 11-05 처럼 한 날에 오늘의 구슬과 특별한 구슬이 **둘 다** 있을 수 있음 (`kind` 가 다르면 같은 날 두 줄)
- 구슬 **색**은 저장하지 않음. 지금은 모두 단색이고, `kind` 로 모양(반짝임)만 구분함 ([A-3](../기획정리_추가정리필요요소.md))

## 칸(컬럼) 설명

| 칸 | 뜻 | 예시 | 비고 |
| --- | --- | --- | --- |
| `id` | 구슬 고유 번호 | `b2c3d4e5-…` | uuid. `answers.ball_id` 가 이 번호를 가리킴 |
| `user_id` | 누구의 구슬인가 | `a1b2…` | `auth.users` 의 id. 기본값 `auth.uid()` |
| `kind` | 구슬 종류 | `short` / `long` | `short` = 오늘의 구슬(단기 질문의 답), `long` = 특별한 구슬(장기 질문의 답). **[questions.kind](02-questions.md) 와 같은 값**. 허용값 두 개만 |
| `ball_date` | 구슬이 생긴 날 (사용자 현지 날짜) | 2026-11-21 | 유리병이 날짜별로 펼쳐지는 기준. 한 달 = 유리병 1개 |
| `score` | 퇴사각 지수 (0~100) | 55 | 높을수록 퇴사각↑. 구슬을 누르면 **숫자로만** 보임. 계산 방식은 [A-10](../기획정리_추가정리필요요소.md) |
| `created_at` | 구슬이 처음 생긴 시각 | 2026-11-21 16:10 | |
| `updated_at` | 점수가 마지막으로 바뀐 시각 | 2026-11-21 16:15 | 오늘의 구슬은 2 · 3번째 답을 하면 `score` 가 다시 계산됨 |

### 퇴사각 지수(score) 계산 — 임시 규칙
- **오늘의 구슬**: 그날 답한 단기 질문의 **점수 평균** (답 1개면 그 점수)
- **특별한 구슬**: 이달의 질문 답 **1개의 점수**
- 이 규칙은 [A-10](../기획정리_추가정리필요요소.md) 이 정해지기 전의 가장 단순한 안임. 기존 안(최근 7일 · 장기 점수를 섞음)으로 바뀌어도 **칸 구조는 그대로**고 계산 함수만 바뀜
- 점수를 구슬에 **저장해 두는 이유**: 구슬을 누를 때마다 답변을 모아 다시 계산하지 않아도 되고, 나중에 계산식이 바뀌어도 그날 보여준 값이 유지됨(다시 계산할지는 그때 결정)

## 유리병은 테이블이 아님
- 기획의 "유리병 1개 = 한 달"은 **`ball_date` 의 달로 묶은 것**일 뿐이라 `balls` 말고 **유리병 테이블은 만들지 않음**

| 화면 | 가져오는 방법 |
| --- | --- |
| 이번 달 병 (채우는 중) | `ball_date` 가 이번 달인 내 구슬 |
| 지난 달 병들 (선반 진열) | `ball_date` 의 달별로 묶음 (답한 달만 병이 보임) |
| 병을 눌렀을 때 날짜별로 펼치기 | 그 달의 구슬을 `ball_date` 순으로 |
| 구슬을 눌렀을 때 하루 기록 | `answers` 에서 `ball_id = 그 구슬` 인 줄 → 질문 · 고른 답 |

## 다른 테이블과 연결
> **구슬 하나에는 답이 1~3개 담긴다** (오늘의 구슬 1~3개, 특별한 구슬 1개)

```
auth.users ──< balls >──< answers >── question_deliveries
  (누구의)    (구슬)       (답 한 줄)     (나온 질문)
```

- 사용자 1명 → 구슬 **여러 개**
- 구슬 1개 → 답 **1~3개** (`answers.ball_id`)
- `ball_id` 를 `answers` 에 둔 이유: 구슬을 누르면 그 답들을 바로 찾을 수 있고, 특별한 구슬 ↔ 장기 답이 헷갈리지 않음 ([answers 메모](04-answers.md))

## 어떻게 만들어지나 (DB 함수)

앱이 `balls` 를 직접 만들지 않음. [`submit_answer`](04-answers.md) 함수가 답을 저장하면서 같이 처리함

| 답한 질문 | 함수가 하는 일 |
| --- | --- |
| **단기** 첫 답 | 오늘의 구슬을 **새로 만들고**(`short`) 답을 담음 → 앱에 "새 구슬 생김"을 알려 줌 → 구슬 넣기 연출 |
| **단기** 2 · 3번째 답 | 이미 있는 오늘의 구슬에 답을 담고 `score` 평균을 다시 계산 → **새 구슬 없음**, 연출 없음 |
| **장기** 답 | 특별한 구슬을 **새로 만들고**(`long`) 답을 담음 → 구슬 넣기 연출 |

- "오늘 구슬이 이미 있는지"는 `unique (user_id, ball_date, kind)` 가 보장 → 두 번 눌러도 **구슬이 2개로 늘지 않음**
- **구슬 넣기 연출은 저장하지 않음**: 함수가 "새 구슬이 생겼는지" 값만 돌려주고, 연출은 앱이 보여줌
- 사용자가 따로 할 일 없음 (기획: "답하기만 하면 구슬이 생김")

## SQL 초안

```sql
create table balls (
  id         uuid primary key default gen_random_uuid(),
  user_id    uuid not null default auth.uid() references auth.users(id) on delete cascade,
  kind       text not null check (kind in ('short', 'long')),
  ball_date  date not null,                    -- 사용자 현지 날짜
  score      numeric not null check (score between 0 and 100),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (user_id, ball_date, kind)            -- 하루에 종류별 1개
);
-- unique 인덱스가 (user_id, ball_date) 조회(유리병 · 선반)도 함께 처리함

alter table balls enable row level security;

-- 내 것만 읽기. insert / update / delete 정책은 만들지 않음 → 변경은 DB 함수만
create policy "내 구슬만 읽기" on balls
  for select to authenticated using (user_id = (select auth.uid()));
```

- **만드는 순서**: `balls` → `answers` (answers 가 `ball_id` 로 balls 를 가리키므로)
- 읽기만 열어 둔 이유: 앱이 `score` 를 직접 고치거나 구슬을 마음대로 만들면 조작할 수 있어서

## 결정 · 메모
- **`short` 구슬은 하루 1개, `long`(특별한) 구슬은 한 달 1개**: 하루 1개는 `unique (user_id, ball_date, kind)` 가 막음. **한 달 1개는 DB 가 아니라 `question_deliveries` 가 막음** (이달의 질문은 `M:연-월` 로 한 달에 한 번만 나오고, 답은 1개뿐이라)
- **구슬 색 · 모양을 저장하지 않음**: 단색(A-3)이고 모양은 `kind` 로 정해짐. 점수별 색은 나중에 `score` 로 정하면 됨
- **`updated_at` 이 있는 이유**: 오늘의 구슬은 답이 늘면 점수가 바뀌어서. 특별한 구슬은 한 번 만들면 안 바뀜
- **답한 날만 구슬이 있음**: 0개 답한 날은 줄이 없음 (기획 "그날은 구슬 없음"). 구슬이 없는 날은 유리병에서 빈 자리로 보이게 앱이 처리
- **legacy 와 달라진 점**: 색에 점수를 반영하지 않음(단색), 퇴사각 지수는 숫자로만 보여줌. 구슬 모양 · 병 위치 · 병 숨기기 같은 기존 화면 내용은 [A-4](../기획정리_추가정리필요요소.md) 에 따라 삭제됨
- **미정**
  - [A-10](../기획정리_추가정리필요요소.md) 퇴사각 지수 계산 방식: 평균만 쓸지, 최근 7일 · 장기 점수를 섞을지. 섞는다면 `score` 에 그 값을 저장
  - 답이 1개뿐인 날도 그대로 보여줄지 (질문마다 점수 기준이 달라 날짜끼리 비교가 어려움)
  - 2 · 3번째 답을 했을 때 반응: 없음 / 유령 한마디 ([A-2](../기획정리_추가정리필요요소.md))
  - 장기 질문이 나오는 날, 오늘의 질문도 **같이** 나오는지 (같이 나오면 그날 구슬이 2개: `short` + `long`)
  - `ball_date` 의 "하루"는 **사용자 현지 날짜** 기준 → 시간대 처리는 개발 때 확인 ([question_deliveries 메모](03-question-deliveries.md))
