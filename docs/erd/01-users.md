# 1. users — 사용자 (`auth.users` 를 그대로 씀)

> **결정 (A안)**: public 에 users 테이블을 따로 만들지 않음. Supabase 가 관리하는 `auth.users` 를 사용자 명단으로 그대로 씀
> 배경: [Supabase 구조](00-supabase-구조.md) 2 · 3

## 왜 필요한가
- 이 앱의 모든 기록(답변, 구슬, 유령, 설정)은 **"누구의 것인지"** 가 있어야 함
- 그래서 가장 먼저, 가장 가운데에 오는 것
- 기획 근거: [기획정리.md](../기획정리.md) 9. 설정의 "계정 연결", 11. 저장되는 정보

## 예시 데이터 (`auth.users` — Supabase 가 자동으로 만듦)

| id | email | is_anonymous | created_at |
| --- | --- | --- | --- |
| `a1b2…` | hyeri@example.com | false | 2026-11-18 09:00 |
| `c3d4…` | (비어 있음) | true | 2026-11-19 14:30 |

- 첫 번째 줄: 계정을 연결한 사용자
- 두 번째 줄: 아직 계정을 연결하지 않은 사용자 (익명 로그인) → email 이 비어 있어도 앱은 쓸 수 있음
- 실제로는 비밀번호(암호화), 로그인 기록 등 칸이 더 있지만 **우리가 신경 쓸 칸은 위 4개**

## 칸(컬럼) 설명

| 칸 | 뜻 | 예시 | 비고 |
| --- | --- | --- | --- |
| `id` | 사용자마다 붙는 **고유 번호** | `a1b2c3d4-…` | 겹치지 않는 긴 랜덤 문자열(uuid). 다른 테이블이 "누구 것"인지 이 번호로 가리킴 |
| `email` | 연결한 계정 이메일 | hyeri@example.com | 계정 연결 전에는 비어 있음 |
| `is_anonymous` | 익명 사용자인지 | true / false | 계정을 연결하면 false 로 바뀜. **id 는 그대로** |
| `created_at` | 처음 앱을 실행한 시각 | 2026-11-18 09:00 | |

- 이 칸들은 **우리가 만들거나 고치지 않음.** 로그인 기능이 알아서 채움
- 앱에서 이 테이블을 **표처럼 직접 조회할 수는 없음.** 대신 로그인 기능(`supabase.auth.getUser()`)으로 **로그인한 본인의 정보(id, email, 익명 여부)** 는 받을 수 있음 → 설정의 "연결된 계정: hyeri@…" 표시는 public.users 없이 가능

## 다른 테이블과 연결
> **사용자 한 명은 여러 개의 기록을 가진다**

```
auth.users (1명)
  ├── 받은 질문 여러 개
  ├── 답변 여러 개
  ├── 구슬 여러 개
  ├── 유령 1마리
  └── 설정 1세트
```

- 다른 테이블에는 `user_id` 칸이 생기고, 거기에 `auth.users` 의 `id` 를 적음 → "이 답변은 a1b2… 사용자 것"
- 나머지 테이블을 만들 때마다 이 그림에 선이 하나씩 늘어남

## 결정 · 메모
- **public.users 는 만들지 않음 (A안, 2026-11-18)**: 지금 기획에서는 앱이 보여줄 사용자 정보가 없음. 이메일도 `auth.users` 에 이미 있음
- 나중에 관리자 웹 · 개인정보 동의 · 이용 정지 등이 필요해지면 같은 id 로 `public.users` 를 추가 → 다른 테이블은 그대로 ([Supabase 구조](00-supabase-구조.md) 3)
- 계정 연결 전 사용자는 Supabase "익명 로그인" 으로 id 를 먼저 받고, 나중에 이메일을 연결함 (임시)
